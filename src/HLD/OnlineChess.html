Step 2

Requirements

✅ Functional

  • Player joins matchmaking queue (with timestamp)
  • System pairs players FCFS — earliest-waiting gets matched first
  • Matched players receive game session details
  • Player can cancel queue at any time
  • Disconnected players are cleaned up automatically
  • No player matched more than once

⚙️ Non-Functional

  • Latency: Match within <5s for p95
  • Throughput: 1M concurrent queue entries
  • Availability: 99.99% uptime for matchmaking
  • Consistency: No double-matching (exactly-once semantics)
  • Scalability: Horizontally scalable to millions
  • Fault Tolerance: Survive pod/node failures gracefully

🚫 Out of Scope (V1)

  • Elo / skill-based matchmaking
  • Game logic (moves, board state)
  • Tournament brackets
  • Spectator mode
  • Chat system

Key insight: 1M queue entries × 100 bytes = ~100MB. A single Redis node fits this easily. Sharding is for throughput (write rate), not memory size.

Write Rate Estimate

Queue join rate: ~1M players joining per 60s = ~16,700 writes/sec Queue dequeue: Same rate ~16,700 dequeues/sec (paired matches) Heartbeat writes: 1M players × 1 heartbeat/10s = 100,000 writes/sec (dominant) WebSocket msgs: ~16,700 match notifications/sec

Heartbeat is the highest-frequency operation. Design the heartbeat to be lightweight (EXPIRE refresh only) and never touch the sorted set.

Step 7

Concurrency & Double-Match Prevention

Core concurrency problem: Multiple matchmaking engine pods running simultaneously could each read the same 2 players from the ZSET and create duplicate matches. This is the critical race condition to solve.

Solution: Single-Owner Sharded Architecture

Each regional queue is owned by exactly ONE matchmaking engine worker at a time. Workers acquire a distributed lock (Redis SETNX) over the shard they process. This eliminates races at the design level.

Queue Shards: ┌──────────────────────────────────────────────────────────┐ │ matchmaking:queue:us-east:0 → Worker Pod A (lock held) │ │ matchmaking:queue:us-east:1 → Worker Pod B (lock held) │ │ matchmaking:queue:us-east:2 → Worker Pod C (lock held) │ │ matchmaking:queue:us-east:3 → Worker Pod D (lock held) │ └──────────────────────────────────────────────────────────┘ Players are assigned to a shard via: hash(playerId) % NUM_SHARDS Each pod only processes ONE shard → no two pods compete for the same players

Atomic Lua Script (Safety Net)

Even with sharding, we use a Lua script executed atomically in Redis as a final safety net. Redis is single-threaded for command execution, so a Lua script is always atomic:

Lua script — atomic pair-and-claim
-- KEYS[1] = queue key (ZSET)
-- KEYS[2] = player1 heartbeat key
-- KEYS[3] = player2 heartbeat key
-- ARGV[1] = player1Id, ARGV[2] = player2Id

local alive1 = redis.call('EXISTS', KEYS[2])
local alive2 = redis.call('EXISTS', KEYS[3])

if alive1 == 0 or alive2 == 0 then
  return redis.error_reply("PLAYER_DEAD")
end

-- Check both are still in QUEUED state
local s1 = redis.call('HGET', 'player:state:'..ARGV[1], 'status')
local s2 = redis.call('HGET', 'player:state:'..ARGV[2], 'status')

if s1 ~= 'QUEUED' or s2 ~= 'QUEUED' then
  return redis.error_reply("ALREADY_MATCHED")
end

-- Atomically remove from queue + transition state
redis.call('ZREM', KEYS[1], ARGV[1])
redis.call('ZREM', KEYS[1], ARGV[2])
redis.call('HSET', 'player:state:'..ARGV[1], 'status', 'RESERVED')
redis.call('HSET', 'player:state:'..ARGV[2], 'status', 'RESERVED')

return "OK"

Failure Handling

Failure Scenarios & Mitigations

FailureDetectionRecovery
Player disconnects before matching Heartbeat TTL (30s) expires — Redis key auto-deleted Background janitor job scans for QUEUED players whose heartbeat key is missing → ZREM from queue, mark TIMED_OUT
Player disconnects while in RESERVED state Heartbeat TTL expires during session creation Engine detects PLAYER_DEAD from Lua script → rolls back: ZREM of live player re-enqueued at front (preserving wait time), RESERVED player marked TIMED_OUT
Matchmaking Engine pod crashes mid-match RESERVED state with no match event after 5s A recovery daemon polls for RESERVED players older than 5s → re-enqueues them with original join timestamp (maintaining FCFS order)
Game Session Service is down HTTP timeout from engine after session creation call Both players set back to QUEUED, re-inserted at head of queue with original timestamp. Retry with exponential backoff + circuit breaker.
Redis node failure Redis Sentinel / Cluster failover Redis Cluster (3 primary + 3 replica shards) — automatic failover in <30s. In-flight RESERVED entries may be lost → recovery daemon re-queues on restart.
Kafka consumer (WS Gateway) lag Consumer group lag monitoring Players are already MATCHED in Redis (source of truth). Client polls GET /queue/status as fallback if WS push is delayed >3s.
WebSocket connection drops after match Client reconnects → sends playerId Client re-subscribes to WS Gateway → Gateway checks Redis for MATCHED status → resends game URL
Golden rule: Redis is the source of truth for real-time state. PostgreSQL is the audit trail. Kafka is the fan-out bus. Any component can crash and recover by consulting Redis state.

Janitor / Recovery Service

Recovery Daemon (runs every 5s): 1. SCAN player:state:* WHERE status = RESERVED AND updatedAt < (now - 5s) → Re-enqueue with original joinedAt timestamp (FCFS preserved) → ZADDOPTION NX — only add if not already present 2. SCAN player:state:* WHERE status = QUEUED → EXISTS player:heartbeat:{id} → if 0: ZREM from queue, mark TIMED_OUT 3. Emit metrics: queue_depth, reserved_stuck_count, timeout_count

Scalability Design

Queue Sharding Strategy

Shard Assignment: shard = hash(playerId) % NUM_SHARDS ┌─────────────────────────────────────────────────────────┐ │ REGION: us-east (4 shards, 4 workers) │ │ │ │ Shard 0 [matchmaking:queue:us-east:0] ◄── Worker A │ │ Shard 1 [matchmaking:queue:us-east:1] ◄── Worker B │ │ Shard 2 [matchmaking:queue:us-east:2] ◄── Worker C │ │ Shard 3 [matchmaking:queue:us-east:3] ◄── Worker D │ └─────────────────────────────────────────────────────────┘ Scale horizontally: add shards + workers as load grows. Minimum 2 players per shard needed to match → cross-shard merge for odd cases.
Odd-queue problem: If a shard has only 1 player, they can't be matched within that shard. Solution: if queue depth = 1 for >2s, the worker can peek at adjacent shard's oldest player and perform a cross-shard match using a distributed lock over both shards.

Regional Deployment

WebSocket Gateway Scaling

WS connections are stateful — a player's connection is pinned to one pod. When a match event is published to Kafka, ALL WS Gateway pods consume it. Each pod checks its in-memory connection map for the player's connection. Only the pod holding the connection pushes the message.

WS Pod A: holds connections for players [1,2,5,7...] WS Pod B: holds connections for players [3,4,6,8...] Kafka event: { p1: "player1", p2: "player3" } → WS Pod A receives event → finds player1 → pushes MATCHED → WS Pod B receives event → finds player3 → pushes MATCHED → Both pods find nothing for the other player → no-op
Step 10

Optimizations

⚡ Latency

  • Engine polling interval: 50ms (adjustable). At 8K matches/sec, 50ms gives 400 matches/cycle — well within budget
  • Batch ZRANGE: Fetch top 20 pairs per cycle, not just 2 — amortizes Redis round trip
  • Long polling fallback: Clients that can't hold WS use long-poll GET /queue/status with 5s timeout
  • Pre-warm connection pools: Redis and DB connection pools initialized at startup, not lazily

📈 Throughput

  • Redis pipeline: Batch heartbeat refreshes using PIPELINE to reduce RTT
  • Kafka partitioning: Partition match-events by region — WS pods for a region only read their partition
  • Async DB write: PostgreSQL match record written asynchronously after Kafka publish — not in critical path
  • Stateless API pods: All state in Redis → horizontal scale with zero coordination

🛡️ Reliability

  • Circuit breaker: Game Session Service wrapped with Resilience4j — degrade to "session pending" if unavailable
  • Idempotent match creation: Game Session Service uses matchId as idempotency key — retries safe
  • Dead-letter queue: Failed Kafka events → DLQ for manual inspection + replay
  • Observability: queue_depth, match_latency_p99, timeout_rate metrics → PagerDuty alert if queue depth spikes

🔮 V2 Extensions

  • Elo-based matching: Replace pure FCFS with priority score = wait_time_bonus + elo_diff_penalty
  • Smart cross-shard merging: If player waits >10s, expand to adjacent shards
  • Predictive pre-warm: ML model predicts queue surge → pre-scales workers 60s ahead
  • Geo-routing: Route player to closest region's queue to minimize game latency

Step 11

Expected Cross-Questions & Answers

Q: Why Redis ZSET instead of a Kafka queue for FCFS?
Kafka is append-only and great for fan-out, but it doesn't support random deletion (cancellation). When a player cancels, I need to remove their entry from the middle of the queue. Redis ZSET supports O(log N) ZREM, making cancellations cheap. Kafka would require a tombstone pattern with compaction, which adds complexity. Redis ZSET is the right data structure for a mutable, ordered, real-time queue.
Q: What if Redis goes down?
Redis Cluster provides automatic failover (30s max). During that window, new joins are rejected with 503 (graceful degradation). In-flight RESERVED entries are lost — recovered by the recovery daemon which re-enqueues from PostgreSQL's queue_events audit log. The queue was in memory; we accept that brief disruptions may re-order a small number of players — FCFS is restored on recovery.
Q: How do you prevent two engine workers from matching the same player (race condition)?
Two-layer defense: (1) Single-owner architecture — each shard is processed by exactly one worker at a time using a distributed lock (Redis SETNX with TTL). (2) Atomic Lua script — even if shard ownership somehow overlaps, the Lua script checks and transitions status atomically. If two workers both run the script for the same player, the second one sees status ≠ QUEUED and returns ALREADY_MATCHED — no double-match.
Q: How does the system handle 1 million concurrent WebSocket connections?
WS Gateway pods use Java NIO (Netty) which handles 100K+ connections per pod on a single machine using event-driven I/O. For 1M connections, we need ~10 pods. Connections are sticky via the load balancer (IP hash). Each pod maintains an in-memory HashMap of playerId → WS channel. Kafka events broadcast to all pods; only the pod holding the connection pushes the message. Horizontal scaling is straightforward — add more pods.
Q: Is your FCFS truly global? What about cross-shard fairness?
No — it's FCFS within a shard, not globally strict. A player in shard 0 and a player in shard 1 with the same join time might be matched in different order. This is an intentional design choice: global FCFS would require a single-threaded global queue which cannot scale. In practice, since players are hashed to shards deterministically, and shards are processed at the same polling rate, cross-shard fairness deviation is on the order of one poll interval (50ms) — imperceptible to users. I'd call this "practical FCFS" in the interview.
Q: Why Kafka between Matchmaking Engine and WebSocket Gateway? Why not direct Redis pub/sub?
Redis pub/sub is fire-and-forget — if the WS Gateway pod is temporarily down or lagging, messages are lost. Kafka provides durability (message retained for 24h), replay capability, and at-least-once delivery guarantees. The WS Gateway uses Kafka consumer group offsets — on restart it replays missed events. Also, Kafka decouples the producer (engine) from consumer (WS Gateway) — we can add more consumers (audit, analytics) without touching the engine.
Q: How do you handle a player who gets RESERVED but then disconnects?
The heartbeat key for the RESERVED player expires in 30s. The recovery daemon, running every 5s, scans for players in RESERVED state whose heartbeat key is gone. It re-enqueues the other (live) player at the head of the queue with their original join timestamp — preserving their FCFS position. The disconnected player is marked TIMED_OUT and their session is cleaned up. No player is left in an inconsistent state.
Q: How would you add Elo-based matchmaking without breaking FCFS?
Create separate Redis ZSETs per Elo bracket (e.g., 1000-1200, 1200-1400, 1400+). Players join the queue in their bracket. FCFS is preserved within each bracket. For players waiting >10s without a match in their bracket, the engine expands the search to ±200 Elo (configurable). This is a priority queue with time-decayed skill tolerance — a standard extension of FCFS matching.
💡 Interview Closing Line
"To summarize: I scale the queue by sharding Redis ZSETs with single-owner workers, preserve FCFS within each shard, prevent double-matching via atomic Lua scripts, handle disconnections via TTL-based heartbeats and a recovery daemon, and push matches to clients over WebSocket backed by Kafka for durability. The system is horizontally scalable, stateless at the API layer, and has no single points of failure."
